# 0054: Make model-request order and metadata separation explicit

Date: 2026-08-15
Status: accepted; ExECT v17–v21 measured as unselected development candidates
Amends: [decision 0015](0015-model-facing-prompt-language-must-drop-internal-architecture-vocabulary.md)
Related: [decision 0053](0053-gan-structured-events-final-prompt.md)
Does not change: selected ExECT prompt `v0.9.24`, saved v16 evidence,
clinical rules, deterministic repair, scorer, or holdout policy

## Decision

Model requests must define their model-visible system text, section order, and
metadata boundary deliberately. Framework defaults and JSON serialization must
not decide instruction priority or expose research identifiers by accident.

For the ExECT structured-event path, the next request-shape candidate is
`exectv2_hybrid_key_family_event_ledger_v17`:

- the system message is only: “Extract structured clinical events from the
  supplied clinical letter. Return the requested output fields exactly.”;
- the user JSON follows its authored semantic order: `task`, `output_schema`,
  `family_guidance`, `attribute_vocabulary`, `clinical_rules`,
  `worked_examples`, then `letter_text`;
- `prompt_version` and `letter_id` remain in run records but are absent from
  the model-facing request;
- rendered-message tests, not source-dictionary tests alone, own this contract.

v16 remains unchanged. Its measured result belongs to the exact request it saw.
v17 is a new identity because request order, system text, and visible metadata
can change model behavior even when the clinical instructions are otherwise the
same.

## Mistake being corrected

The v16 Python dictionary was written in a sensible order, but
`json.dumps(..., sort_keys=True)` alphabetized the model-facing JSON. The model
therefore saw the large attribute vocabulary first, the patient letter in the
middle, and the detailed task near the end. The serialization option silently
overrode the prompt design.

DSPy's default chat adapter also expanded a small extraction signature into a
911-character system preamble describing internal field mechanics and showing
a literal `{prompt_input_json}` placeholder. The actual JSON appeared once in
the user message, but the generated preamble added structure the task did not
need.

Finally, the user JSON exposed `letter_id` and the full prompt-version name.
Those values support provenance and reproducibility; they do not help a model
extract clinical facts. Mixing research metadata with model instructions was a
boundary error.

This was an important prompt-engineering mistake because the effective prompt
is the rendered provider request, not the source dictionary or DSPy signature.
Reviewing only source objects concealed both the reordered sections and the
generated system text.

## Durable requirements

For new or changed model-facing prompts in this repository:

1. Render the complete provider messages for at least one permitted example.
2. Assert the top-level section order when order is intentional.
3. Keep task and output requirements before supporting reference material;
   place the current source text after reusable examples unless a protocol
   states another order.
4. Keep prompt versions, row identifiers, split names, run identifiers,
   component names, and scoring notes outside model-facing messages unless the
   model needs a specific item to perform the task.
5. Keep provenance in run artifacts even when it is removed from model input.
6. Give any behaviorally different rendered request a new prompt identity.
7. Preserve historical builders needed to interpret saved results.

These requirements apply to system messages generated by frameworks as well as
JSON or prose written directly in this repository.

## Evidence and verification

The no-call EA0002 render for v17 shows:

- system message: 110 characters, with no generated field-description preamble;
- user JSON order: `task`, `output_schema`, `family_guidance`,
  `attribute_vocabulary`, `clinical_rules`, `worked_examples`, `letter_text`;
- no model-visible `prompt_version`, `letter_id`, or `EA0002`;
- the complete user JSON appears once;
- the prompt-only run row still records
  `exectv2_hybrid_key_family_event_ledger_v17`.

The focused prompt-contract suite passes 26 tests and pins the v16 request as
the legacy contract. The v17 20-letter Luna batch had zero call or parse
failures but remained below v0.9.24 on SF. The v18 sink clarification improved
v17's hybrid headline and SF on the same frozen pool, with zero call or parse
failures, but still had a historical single-event over-read. The v19
present/ongoing guard corrected that row and raised the dev20 result further,
also with zero call or parse failures. v20 then combined a clause-local count
binding rule with an explicit seizure-free anchor and regressed SF and
exactness; v21 isolated the clause-local rule and still regressed SF,
Diagnosis, headline, and exactness, again with zero call or parse failures.
See the v17–v21 study reports for the bounded measurements.

## Research and promotion boundary

v17–v21 were implemented and measured, but none is selected. The dated
v17–v21 study protocols and the prompt-convention migration campaign
note are pruned from the working tree; recover them from Git history if
a later study needs the exact predeclaration text. Living prompt
identity is the three-slot assignment under
[prompt variant slots](../research/exectv2/prompt_variant_slots_2026-08-16.md)
(`v0.9.24` selected). A later decision is required to select a prompt
or change a reported fill. `test60` stays sealed.
